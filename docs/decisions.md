## 001 — PostgreSQL

**Context.** We need advanced SQL (window functions over time windows), referential integrity and
a database the API can query online.

**Decision.** PostgreSQL 16 in Docker.

**Alternatives.**
- *SQLite:* no `RANGE BETWEEN INTERVAL` in windows, no concurrency for the API.
- *DuckDB:* excellent for offline analytics, but not a transactional database to serve the API.
- *Parquet + pandas:* no constraints or real SQL; it misses the goal of demonstrating SQL.

**Consequences.** Docker is required. `COUNT(DISTINCT)` is not supported in window functions →
some features need `LATERAL` (and their performance must be measured).

---

## 002 — Scenario-based synthetic dataset

**Context.** No public dataset combines customers, cards, merchants, devices and real timestamps
(see `phase1_design.md` §3.1).

**Decision.** Our own simulator, where fraud is generated by behavioural scenarios (card testing,
ATO, cloning, fraud rings, compromised merchant, stealth), with noise in behaviour and labels. The
generator is frozen and versioned before modelling.

**Alternatives.** IEEE-CIS (rich but anonymous and not redistributable), Sparkov/TabFormer (no
devices).

**Consequences.** Risk of circularity: the model may learn the generator's rules. Stated openly;
the project demonstrates methodology, not findings about real fraud. Advantage: the ground truth of
scenarios and data quality defects is known, which makes it possible to measure the recall of the
DQ rules and to analyse errors by scenario.

---

## 003 — Labels with a report date

**Context.** In card fraud the label arrives days or weeks later (chargeback).

**Decision.** A `core.fraud_labels(transaction_id, is_fraud, reported_at, label_source)` table
instead of a `transactions.is_fraud` column.

**Alternatives.** A boolean column in `transactions` (simpler, but it hides the problem of when the
label becomes available).

**Consequences.** Every label-derived feature must filter `reported_at < ts`. Performance
monitoring has to wait for labels to mature.

---

## 004 — Point-in-time SQL features shared offline/online

**Context.** Historical features are the main source of leakage and of training/serving skew.

**Decision.** Each feature is defined once in SQL using only history with a strictly earlier `ts`.
The current transaction does not count in its own velocity. Offline it is materialised for the
whole table; online it is computed for a single transaction. A parity test compares both.

**Alternatives.** A feature store (Feast): it solves the same with more infrastructure than we
need. Features in pandas: more flexible, but it misses the SQL goal and duplicates logic with the
API.

**Consequences.** Some features may be slow in SQL; if so, it is measured and the chosen
alternative documented (it happened: decision 017).

---

## 005 — Temporal validation

**Context.** Fraud happens in campaigns and features depend on time. A random split puts the same
campaign and the same card in both train and test.

**Decision.** Train 12 months (TimeSeriesSplit with a gap for tuning) → validation 3 months
(calibration and thresholds) → test 3 months (a single evaluation) → simulated production 6 months.

**Alternatives.** A random stratified `train_test_split`: used only to *measure* how much it
overestimates (hypothesis H7).

**Consequences.** Less training data than with random CV; more pessimistic and more credible
results.

---

## 006 — PR-AUC as the selection metric

**Context.** Expected base rate ~1%.

**Decision.** Select models by PR-AUC (Average Precision); choose the policy by expected cost in €.

**Alternatives.** Accuracy (a model that approves everything would get ~99%); ROC-AUC (reported, but
with extreme imbalance it can be high with poor precision, because true negatives dominate the
false positive rate).

**Consequences.** PR-AUC must be communicated next to the base rate to be interpretable.

---

## 007 — Decision policy optimised on an amount-dependent cost

**Context.** The goal is to minimise cost, not errors. Letting a €2 fraud through does not cost the
same as a €2,000 one, and review capacity is limited.

**Decision.** A cost model with explicit assumptions in `configs/costs.yaml`. Compare global
thresholds (P1) with a per-transaction decision based on expected cost (P2), both under the
capacity constraint, chosen on validation.

**Alternatives.** Flat costs per error type (simpler, less realistic); a fixed 0.5 threshold (no
justification with a 1% base rate).

**Consequences.** P2 requires calibrated probabilities. Results depend on assumptions → a
sensitivity analysis is mandatory.

---

## 008 — No SMOTE by default

**Context.** Minority class ~1%.

**Decision.** Use `class_weight` and threshold tuning. SMOTE only if shown to be necessary.

**Alternatives.** SMOTE / undersampling.

**Consequences.** We avoid generating incoherent synthetic transactions (interpolating two
different card histories) and distorting the probabilities that must be calibrated. Decision 018
went further: no class weights either.

---

## 009 — Minimal stack

**Decision.** Python, PostgreSQL, scikit-learn, FastAPI, MLflow, Docker, pytest, ruff, GitHub
Actions. No Kafka, Airflow, Spark, Kubernetes, feature store or DVC.

**Reason.** Each of those tools solves a scale or operations problem this project does not have;
adding them would add complexity without adding learning about the core problems (leakage, cost,
calibration, drift).

## 010 — Gradient boosting as the final model?

**Status.** Accepted in Phase 7, with evidence:

- Phase 6 (validation, paired comparison by day): gradient boosting beats logistic regression by
  +0.024 PR-AUC (CI +0.015 to +0.033) and random forest by +0.026.
- Phase 7 (temporal CV): 0.803 vs 0.786 for the tuned logistic regression.

The advantage is real but modest. The original decision's rule: if the cost difference (Phase 8)
turned out irrelevant, logistic regression would be preferred for simplicity. It is kept as the
interpretable alternative.

## 011 — Data quality: reject, repair or warn

**Context.** The `raw` extract has duplicates, invalid values, broken references and extreme
values. Deleting everything suspicious is easy, but it removes real data (and fraud).

**Decision.** Each rule has an explicit action in `dq.rules`:
- `reject` when the correct value cannot be known (negative amount, a card of another customer,
  the same `transaction_id` with two different contents).
- `repair` only when the fix is **deterministic**: null `customer_id` → the card's owner; `eur` →
  `EUR`; country of a card-present payment → the merchant's country; device "unknown" → `NULL`.
- `warn` for rare but possible values: extreme amounts and shared devices.

**Alternatives.** Reject everything anomalous (loses real payments); impute likely values such as
`EURO` → `EUR` (guessing is not a rule).

**Consequences.** Online transactions can have `device_id = NULL` (unknown device): the CHECK on
`core.transactions` was relaxed. Outliers are kept: in the full run they are 7.49% real fraud vs
0.99% for the rest.

## 012 — Customers without a country: cascading rejection

**Context.** 30 customers arrive without a country of residence. The country underlies every
geographic feature (cross-border, country change).

**Decision.** Reject the customer and, in cascade, their cards, transactions and labels.

**Alternatives.** Allow a null country in `core.customers` and let features treat it as unknown; or
infer it from their transactions (that would use information after sign-up: leakage).

**Consequences.** 3,094 valid transactions are lost (0.11%). The fraud rate of what is excluded
(0.953%) is similar to that of what is kept (0.995%), so the cleaning does not bias the dataset. If
the problem were frequent in production, the null-country alternative would be better.

## 013 — Simulator v1.0.1: minimum age fix

**Context.** The `CUS_UNDERAGE_ACCOUNT` rule found 448 customers who opened their account up to 12
hours before turning 18. It was not an injected defect: it was a simulator bug, which computed 18
years as 18 × 365.25 days instead of 18 calendar years.

**Decision.** Fix the generator, bump the version to 1.0.1 and add a unit test.

**Consequences.** The dataset hash changes (`a16b1bf8…` → `350d74bd…`). The reports of both
versions are kept in `reports/simulation/`. A good example of why data quality is validated with
business rules and not only with the expected defects.

## 014 — Known artefact: transactions at the period edges

**Context.** The generator clips timestamps to the simulated period. Legitimate transactions whose
local time falls outside the period pile up on the first and last second: 39 at
`2024-07-01 00:00:00` and 54 at `2026-06-30 23:59:59` (0.003%).

**Decision.** Document it and not fix it now. Fixing it requires a new simulator version,
regenerating and re-running data quality, and it would change numbers already published in the
Phase 2 and 3 PRs for a negligible effect.

**Consequences.** If another simulator version is ever needed for another reason, it will be fixed
at the same time (resample instead of clipping). Merchant velocity features on those two seconds
may see an artificial peak.

## 015 — EDA on the training period only

**Context.** The EDA decides which features to build and how. If it looks at validation, test or
production data, those decisions are informed by the data the model is later evaluated on (*data
snooping*): the test result stops being an honest estimate.

**Decision.** The exploratory analysis uses only `train` (2024-07-01 → 2025-06-30, defined in
`configs/splits.yaml`). Of the other periods only row counts are shown.

**Alternatives.** EDA on the whole history (more data, but it contaminates the evaluation).

**Consequences.** The designed drift (2026) was not looked at in the EDA: the Phase 12 monitoring
had to discover it, as in a real deployment.

## 016 — Warm-up excluded from training

**Context.** The extract starts on 2024-07-01 for every customer, although many have been active
for years. In the first months everything looks "new": in July 2024, 76.8% of transactions have
`merchant_new_for_customer = true`, against 24.5% in June 2025. It is a truncated-history bias,
not a change in behaviour.

**Decision.** Models are trained on transactions from 2024-10-01 (`warmup_days` in
`configs/features.yaml`). Features are still computed from the start so that the history exists
when training starts.

> *Correction (Phase 13):* the entry originally said `warmup_days: 90`. 90 days from 2024-07-01
> is 2024-09-29, not the intended 2024-10-01; Phase 6 set it to **92**, which is the value in the
> configuration.

**Alternatives.** Bounded windows (e.g. "merchant not seen in 180 days"): they stabilise the
feature, but need a 180-day warm-up and lose information.

**Consequences.** 3 months of training are lost. `merchant_new_for_customer` still drifts at 12
months: it was watched in monitoring (Phase 12).

## 017 — Offline features with window functions, online with lookups + parity test

**Context.** The design asked for a single definition per feature. In PostgreSQL the efficient way
to compute 2.85M rows (window functions) does not work for a single transaction in the API, and the
natural way for one transaction (LATERAL lookups) is slow for the whole history.

**Decision.** Offline: window functions with `RANGE ... EXCLUDE GROUP` where possible, and LATERAL
only for distinct counts, medians and labels. Online (Phase 10): per-transaction lookups.
Equivalence is guaranteed by tests: a hand-built scenario with expected values, a time-travel test
(deleting the future does not change the past) and, in Phase 10, an offline/online parity test.

**Alternatives.** A feature store; or LATERAL lookups offline too (a single implementation, but a
much slower build).

**Consequences.** Two implementations that can diverge: the parity test was mandatory in Phase 10
(and it found a real divergence: decision 024).

## 018 — No class weights or resampling

**Context.** With 0.73–0.85% fraud, the usual answer is `class_weight="balanced"` or resampling
(SMOTE, undersampling).

**Evidence (validation, Phase 6).** With balanced weights, PR-AUC does not improve (gradient
boosting −0.002, not significant) or gets worse (logistic regression −0.046, paired CI −0.058 to
−0.035), and the mean probabilities go from 0.0072 (observed 0.0073) to 0.068 and 0.123.

**Decision.** Train without weights or resampling. Imbalance is handled in the decision (a
threshold by cost and capacity, Phase 8), which needs calibrated probabilities.

**Alternatives.** SMOTE: besides distorting probabilities like the weights, it creates synthetic
transactions by interpolating between unrelated cards and customers.

**Consequences.** The model's probabilities come out almost calibrated on average; Phase 8 checks
calibration by bands.

## 019 — Models saved with skops and an explicit list of trusted types

**Context.** MLflow 3 saves scikit-learn models with skops. A pickle can run arbitrary code when
loaded; skops only rebuilds types declared trusted.

**Decision.** Keep skops and declare the necessary types in `pipelines.SKOPS_TRUSTED_TYPES` (our
`signed_log1p` function and internal scikit-learn types). A test checks that every pipeline is
saved, reloaded with that list and predicts exactly the same.

**Alternatives.** `serialization_format="cloudpickle"`: it works without a list, but loading a
model becomes running code from a file.

**Consequences.** Any new transformer forces the list to grow; the test detects it.

## 020 — Model selected by temporal CV; validation only confirms

**Context.** The random search (16 configurations × 4 temporal folds) finds a gradient boosting
with 0.803 PR-AUC in CV vs 0.797 for the default configuration. On validation the difference is
+0.002 (paired CI −0.004 to +0.008): not significant.

**Decision.** Select the configuration with the best temporal CV (`selected_model` in
`configs/model.yaml`) without choosing anything by looking at validation. Validation does not
contradict it and it costs nothing more.

**Alternatives.** Go back to the defaults (equally defensible: the improvement is within the
noise); choose by validation (that would tune hyperparameters on validation and turn it into
another training set).

**Consequences.** The variation between months (0.759 to 0.825 in CV) is larger than any tuning
gain: per-month uncertainty must appear in the reports and in monitoring.

**Phase 13 note.** The numbers above came from frames whose row order changed on every load.
Re-run with a fixed order, the search selects the same configuration: 0.803 vs 0.799 in CV,
+0.004 on validation (CI −0.001 to +0.010). The decision stands. The selected parameters are
stored rounded (0.021, 0.68), so the shipped model is not bit for bit the search's best; on
validation it scores 0.792 against 0.794.

## 021 — Per-transaction expected-cost policy (P2)

**Context.** Two ways of turning the probability into a decision: global thresholds (P1: review if
p ≥ 4.4%, block if p ≥ 25%) or choosing for each transaction the action with the lowest expected
cost given p and the amount (P2).

**Evidence (validation).** P2 €62,925, P1 €63,742, block if p ≥ 0.5 €95,162, rules €520,946,
approve all €946,616. On test, P2 €64,098 and P1 €66,962.

**Decision.** Deploy P2. It uses the amount (a €1,000 payment deserves a review at p = 0.55%, a €5
one not until p = 26%) and adapts by itself if the costs change.

**Alternatives.** P1 is easier to explain and only 1.3% more expensive on validation; it would be
the option if the business needed fixed, communicable thresholds.

**Consequences.** P2 needs calibrated probabilities: calibration becomes a requirement watched in
monitoring, not a detail.

## 022 — The test period is evaluated once and recorded in the repository

**Context.** If the test is looked at, something is adjusted and it is looked at again, it stops
being an honest estimate of future performance: it becomes another validation set.

**Decision.** The policy, the calibrator and the model hashes are frozen and committed before
evaluating (`32ce00c`). The evaluation (`fraud policy evaluate-test`) writes
`reports/policy/test_evaluation.json`, which is also committed (`3b95790`); if that file exists the
command refuses to run again unless given `--force`, which must be justified here.

**Result.** PR-AUC 0.752 on test vs 0.792 on validation; policy cost €64,098 vs €946,956 for
approving everything. Published as it is.

**Consequences.** The git history proves the order: first the frozen policy, then the test. The
Phase 13 reproduction from scratch deliberately skipped this step.

## 023 — Explanations with SHAP PermutationExplainer and an additivity check

**Context.** `shap.TreeExplainer` is the fast and exact method for tree models. With
`HistGradientBoostingClassifier` and native categorical splits it silently returns wrong values:
on this model the contributions do not add up to the model output (an error of up to 4.6 log-odds
on every row). It treats categorical splits as numeric thresholds. On a model without categorical
splits the error is 1e-14.

**Decision.** Use `shap.PermutationExplainer` (model-agnostic, exact by construction, slower) and
check on every run that base + contributions = the model's log-odds (largest error obtained:
4.1e-14). Global importance is also measured by permutation, per variable and per family of
variables.

**Alternatives.** Retrain without native categorical splits to be able to use TreeExplainer (it
would explain another model, not the deployed one); use only permutation importance (no individual
explanations).

**Consequences.** Explaining 900 transactions takes ~4 minutes. For the API (Phase 10), explaining
every prediction in real time would be expensive (decision 026).

## 024 — Exact (bit-for-bit) online/offline parity of the model input

**Context.** Decision 017 leaves two implementations of the 50 features. The first parity test
compared with a 1e-9 relative tolerance and passed, but the API and the batch job gave a different
probability for 1 in 150 transactions (0.000732 vs 0.000878 in the case found). Two last-digit
causes:

- pandas' default float parser (`read_csv`), used to build the training data and the batch, does
  not round correctly: `0.002707006369426752` is read 1 ulp low;
- the online SQL computed some features with other types (`ln()` on float8 instead of numeric;
  untyped parameters that PostgreSQL treats as numeric instead of float8).

One ulp matters because tree thresholds fall exactly on repeated training values (for example a
merchant's smoothed rate, shared by many transactions), and a value 1 ulp above takes the other
branch.

**Decision.** The API reads its features with the same function as training and batch (COPY → CSV
→ pandas, `eda.data.query_features`), and the online SQL casts every parameter and intermediate
value to the same type as the offline SQL. The parity test requires exact equality of the 50 model
inputs, and another test requires the API's probability to be the batch one.

**Alternatives.** Read with `float_precision="round_trip"` everywhere (correct, but it changes the
frozen model's inputs: it would require retraining and revalidating); tolerance-based parity (what
failed); rounding the features (changes the model).

**Consequences.** 0 differences in 76,950 values (1,539 production transactions, full database)
and identical probabilities between API and batch. On the next retraining, switch both paths to
`round_trip` together.

## 025 — Online decisions: review capacity with a lock, idempotency and exchange rates

**Context.** The batch job allocates the reviews of a whole day by benefit; the API decides one at
a time. Two simultaneous requests could both see "59 of 60" and both review. The authorisation
system retries: a retry must not score twice or use up a review twice. In the simulated data the
exchange rates end on 2026-06-30, and an exact-day lookup refused any later payment, even in EUR.

**Decision.**
- Capacity first come, first served: review if reviewing is the cheapest and slots are left today;
  otherwise the best alternative (approve or block). Counting and logging happen in one transaction
  under `pg_advisory_xact_lock` per UTC day, only for payments whose best action is a review.
- Idempotency: a unique index on the API's `transaction_id`; a retry returns the decision already
  logged (even if the body changes).
- Exchange rate: EUR without a lookup; other currencies use the latest rate published up to that
  UTC day, and 422 if it is more than 7 days old. Unknown customer, card, merchant or country →
  422: the payment cannot be scored and the authorisation system applies its fallback rule.

**Alternatives.** Reserve slots by the day's expected volume (needs a forecast); decide at the end
of the day (impossible at authorisation); a counter in Redis (another service).

**Consequences.** With the Phase 8 policy the capacity was never reached (at most 41 of 60 in the
production batch), so API and batch decide the same. A test sends 10 simultaneous payments with 3
slots and gets exactly 3 reviews. If capacity started to bind, first come first served would be
worse than the batch's allocation: mediocre morning reviews could take the slot of better ones in
the afternoon. Watched in Phase 12.

## 026 — The service scales with processes; explanations off the request path

**Context.** The Python work per request (reading the features, the prediction of 400 trees for one
row, ~9 ms, and validation) holds the GIL: in a single process, several threads do not increase
throughput (measured in `reports/serving/phase10_findings.md`). Limiting OpenMP threads does not
change the latency of one row (8.8 vs 8.9 ms). Decision 023 left open explaining every prediction:
with `PermutationExplainer` it costs ~0.27 s per transaction.

**Decision.** Scale with processes (replicas or workers behind a load balancer) and one OpenMP
thread per process. `/predict` does not return explanations: the features logged in
`scoring.predictions.features` allow any decision to be explained later, offline or with an
on-demand endpoint.

**Alternatives.** Compile the model (treelite, ONNX) to cut the ~9 ms; group requests
(micro-batching); async endpoints (they do not help with CPU work).

**Consequences.** On this Windows machine, `uvicorn --workers N` fails to start some workers
(`WinError 10022` when sharing the socket); the benchmark starts independent processes on
consecutive ports and spreads requests like a load balancer. The plan to use `--workers` in Docker
was replaced in Phase 11 by `fraud serve api` (decision 027).

## 027 — Two Docker images, versions pinned to the training environment, model mounted

**Context.** The API only needs the serving part: features, model and policy. MLflow, SHAP and
matplotlib are only needed to train and analyse (phases 6–9), and the API imported them
indirectly. Also, a model must be served with the libraries it was trained with: another
scikit-learn version can load the file and score differently without any warning.

**Decision.**
- One `Dockerfile` with two targets: `app` (API and `fraud serve` commands, base dependencies only)
  and `train` (the whole pipeline, with the `train` extra of `pyproject.toml`).
- Dependencies are installed from lock files generated inside the base image, constrained to the
  versions of the training environment (`docker/lock.sh`, `docker/training-env-constraints.txt`).
  The Python base image is pinned by digest.
- The model bundle is not copied into the image: it is mounted read-only. The image is code; the
  model is a separately versioned artefact, as it would be in a model registry.
- The API runs as an unprivileged user, with a read-only filesystem and a healthcheck.
- `fraud serve verify-bundle` re-scores the validation period in the environment where it runs and
  compares with the scores saved in Phase 8.

**Finding.** With the same versions, Linux does not reproduce Windows bit for bit:
- the tree output (log-odds) is identical on all 359,220 transactions;
- 1,446 probabilities differ by 1–2 ulps (1.1e-16): the sigmoid uses the `exp()` of each operating
  system's maths library;
- no decision changes.

So `verify-bundle` reports the exact result and passes up to 4 ulps. A larger difference would mean
another model or other inputs.

**Second finding: `uvicorn --workers` adds ~40 ms per request on Linux.** With several workers,
uvicorn creates the listening socket with protocol 0, and asyncio only enables `TCP_NODELAY` if the
socket declares `IPPROTO_TCP`. Without `TCP_NODELAY`, the response body waits for the client's
delayed ACK. Measured in the container with 4 workers:
- `GET /model` (no work): 44 ms, against 1.3 ms with a single worker;
- `POST /predict`: 88 ms on the client, although the server takes 42 ms.

Fix: `fraud serve api` (`serving/server.py`) starts uvicorn with the same socket declared as TCP.
With it, 0.9 ms and 44.6 ms. A CI step fails if a request that does no work takes over 20 ms. This
corrects the consequence of decision 026, which planned to use `--workers` in Docker.

**Alternatives.** A single image with everything (heavier to serve); copying the model into the
image (one image per model, and data inside a code artefact); unpinned versions (not
reproducible).

**Consequences.** The images weigh 682 MB (`app`) and 944 MB (`train`). In `app`, pyarrow and scipy
take 156 and 139 MB. pyarrow stays because it decides how pandas stores the category strings in the
training environment. Upgrading a library means retraining, regenerating the locks and re-running
`verify-bundle`.

## 028 — CI tests the images end to end with a demo bundle

**Context.** The CI of earlier phases ran lint, unit tests and integration tests with PostgreSQL,
but never built or started an image. The real bundle (Phase 8) is not in git, and training it in CI
would take over 35 minutes.

**Decision.**
- A second job, which only runs if the first passes, builds both images with caching.
- In containers, on the `tiny` dataset: simulate, load, data quality, features and a demo bundle
  (`fraud serve demo-bundle`: a small model in the same format, clearly marked as such).
- It starts the API and compares it with the batch through `fraud serve check`: 50 stored
  payments, the same probability and the same decision. If any differs, CI fails.
- Test coverage (unit + integration) is published on every run, with no minimum threshold for now.

**Alternatives.** Only `docker build` (it does not test that the image works); uploading the real
bundle as a secret or artefact (data and model stay out of the repository by design).

**Consequences.** CI proves that the image starts, connects to the database, loads a bundle and
decides like the batch. It does not test the real model; `verify-bundle` does that locally. With
the `tiny` dataset the demo bundle hardly reviews or blocks (in the local test it approved all 50
payments), so the decision comparison mostly exercises approval.

## 029 — Monitoring "as of" a date, rules fixed before the replay, retraining decided by labels

**Context.** In simulated production (January–June 2026) the simulator injects a drift on 1 March:
more online and wallet payments, and a new wallet fraud pattern. Labels arrive late: a median of 16
days, p90 of 48 and p99 of 104 days. Measuring the performance drop requires waiting, and a
monitoring evaluated with today's data would cheat without noticing.

**Decision.**
- **Each weekly run** (42, from 8 January to 22 October) uses only payments with `ts < date` and
  labels with `reported_at < date`. A test checks that changing later data does not change the
  result.
- **Reference:** the validation period (July–September 2025), where calibration and policy were
  chosen.
- **Signals:**
  - weekly PSI of the 49 model inputs and of the score (bins fitted on the reference, 0 and missing
    values with their own bin), plus KS for information;
  - review and block rates;
  - **delay-adjusted calibration**: frauds reported so far vs those expected so far, `Σ p · F(age)`,
    with F the delay distribution estimated at deployment;
  - recall on mature cohorts (90% of labels expected, about 48 days).
- **Thresholds fixed in `configs/monitoring.yaml` before running the replay.** PSI 0.10/0.25 (the
  industry convention); rates ±25% and ±50%; observed/expected ≥ 1.25 or ≤ 0.80 with p < 0.01;
  recall 5 points below with p < 0.01.
- **Retraining:** only when a label alert repeats in 2 consecutive runs. Input drift alone opens an
  investigation: it says the population changed, not that the model got worse, and retraining needs
  labels from the new regime.
- **Only `monitoring/evaluation.py` reads the simulator's truth, and afterwards.** A test prevents
  any other code from reading it, except the Phase 3 and 9 analyses.

**Alternatives.** Evaluate with every label known today (temporal leakage: the monitoring would look
prescient); use the test period as the reference (it was used once and is not touched again); tune
the thresholds by looking at the replay (they would fit the known drift).

**Consequences.** See decision 030 and `reports/monitoring/phase12_findings.md`.

## 030 — What the replay taught: a fixed PSI threshold fails here, and the rolling reference is a hypothesis

**Context.** Result of the replay with the rules of decision 029, against the drift of 1 March:
- **Delay-adjusted calibration:** an alert after 67 days, with no false alarm before.
- **Retraining recommendation:** after 74 days.
- **Recall on mature cohorts:** after 123 days.
- **Decision rates:** alert earlier (46 days), but they also did in January, for a real fraud peak
  that had nothing to do with the drift.
- **Input PSI at 0.10:** did not detect the drift. After 1 March, the weekly maximum of a stable input
  was 0.090.
- **`device_age_days`** alerted every week from the first one (PSI 1.3–1.7): a device only gets
  older, so it drifts by construction.

PSI did show the change: a step from almost 0 to 0.06–0.075 in the first full week of March, below
the conventional threshold.

**Decision.**
- **The result with the fixed rules is published**, even though it makes PSI look bad.
- **The alternatives designed afterwards are presented as hypotheses**, not as results, and checked
  on 26 drift-free weeks of 2025 that were not used to design them:
  - PSI ≥ 0.05 against the reference: detects after 11 days, but gives 3 false alarms in those 26
    weeks, from variables that accumulate history;
  - **PSI ≥ 0.03 against the previous 4 weeks**, excluding variables whose weekly PSI already exceeds
    0.05 inside the reference: detects after 11 days, with 0 false alarms in 22 drift-free weeks and
    0 before the drift in production;
  - calibration with p < 0.01 only, no ratio threshold: 39 days instead of 67, with no false alarm
    before the drift.
- **Proposal for the next version of the rules:**
  - two views of input drift: a fixed reference for slow changes and a rolling reference for steps;
  - exclude from the fixed reference the variables that drift by construction.

  Validating it needs another drift scenario with another seed and another date.

**A nuance about H9.** What PSI detects early is the change in legitimate behaviour, not the new
fraud. The model still catches 76% of the new fraud, and what gives it away is calibration: more
fraud arrives than the model expects. Hypothesis H9 (PSI detects the drift before labels show the
drop) is not supported with the fixed rules. It only holds with the rule designed afterwards, and
on a different drift from the one that does the harm.

**Consequences.** The rules in `configs/monitoring.yaml` are not changed in this phase, so as not to
rewrite the result. The proposal stays documented for the next iteration.
